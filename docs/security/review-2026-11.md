# Security review — November 2026 (pre-go-live)

Focused application-security review of the whole app before go-live (ARCHITECTURE.md §12
"Before go-live", §15 M3). Scope: authentication and sessions (admin 2FA, fixation, logout),
CSRF on Route Handlers, IDOR on customer-facing routes, open redirects, SSRF, uploads, HTML
injection (rich text, e-mails), rate-limit coverage of public mutations, secret/PII leakage in
logs and responses, security headers on every response, cookie flags, and the OWASP ZAP
baseline warning on the privacy policy pages. Method: code reading of every Route Handler,
storefront Server Action and auth configuration, the generated
[permission review](permission-review.md), and probes against the production build
(`pnpm build` + `scripts/start-standalone.mjs`, demo seed).

Each fix is its own commit with a test. Severity: High = exploitable data/money loss;
Medium = abuse, leakage to third parties or denial of service; Low = defence in depth or a
scanner finding without direct impact.

### F-01 — ZAP "Private IP Disclosure" (rule 2) on the privacy pages

**Evidence.** The weekly ZAP run on `feat/m3w2-gates` (run 43169801539) reported
`WARN-NEW: Private IP Disclosure [2] x 2` for exactly `http://localhost:3200/chinh-sach/bao-mat`
and `http://localhost:3200/en/policies/privacy`. Applying ZAP's regex
(`InfoPrivateAddressDisclosureScanRule.patternPrivateIP`) to the production HTML of both pages
matched `10.0.0.0`, `10.1.0.0`, … `10.4.0.0`, inside the RSC payload:

```
["$","li","10.1",{"className":"my-1 [&>p]:my-0","children":[["$","p","10.1.0",{…
"children":[["$","$1","10.1.0.0",{"children":"Our transactional e-mail provider: …"}]]}]]}]
```

These are React keys built by the rich-text renderer as dotted tree paths (block 10 → list
item 1 → paragraph 0 → text 0). The privacy policy is the only page with more than ten
top-level blocks, so only it produced a `10.x.y.z` key. Not a real disclosure (no address of
ours is rendered), but a true match.

**Fix.** Keys only need to be unique among siblings, so `src/lib/rich-text/react.tsx` now
uses the sibling index. Rendered HTML is unchanged. Rule 2 is listed in `.zap/rules.tsv` as
WARN (with this reference) so a regression is still reported.

### F-02 — HTML responses without a Content-Security-Policy

`src/proxy.ts` sets the page CSP, but its matcher skips `/_next/*` and every path containing
a dot (static files). A miss there (`/wp-login.php`, `/en/missing.html`, `/_next/missing`)
renders the HTML not-found page with the static headers but **no CSP** (verified with curl on
the production build). `next.config.ts` now sends `FALLBACK_CONTENT_SECURITY_POLICY` (the
first-party part of the page policy, `frame-ancestors 'none'`, `object-src 'none'`) on those
sources; API routes keep the deny-all policy (listed last, it wins). Static files ignore CSP.

### F-03 — Coupon brute-force oracle in the checkout quote

`applyCoupon` (cart) is limited to 10 attempts/min/cart (§12), but `quoteCheckoutAction`
accepted any `couponCode` and answered `coupon.applied` / `coupon.issue` without a limit, so
codes could be enumerated through the checkout summary. A code other than the one already
applied to the cart now consumes the same `couponAttempt` bucket before it is evaluated; over
the limit the code is not evaluated at all and the quote answers `couponRateLimited`
(message in `checkout.errors`). Re-quotes with the cart's own code do not count.

### F-04 — Online payment start not rate-limited

`startPaymentAction` creates a payment attempt and calls the gateway API (payOS payment
link, VNPay URL) on every call, guarded only by order access. It now passes the shared
limiter (`RATE_LIMITS.paymentStart`, 10/min/IP) before the order is looked up; the retry
panel shows `checkoutResult.retry.errors.rateLimited`.

### F-05 — Deactivated staff and the admin check

`checkAdminSession` did not look at `users.banned`; deactivation is safe today only because
`deactivateStaff` also deletes the sessions. A banned account now fails the admin check
(`unauthenticated`) even if a session row survived (defence in depth).

### F-06 — Password change and other sessions

§12 requires all sessions revoked on a password change. Better Auth's `/change-password`
keeps other sessions unless the client sends `revokeOtherSessions: true` (the endpoint is
reachable even without a UI for it). A `hooks.before` entry in `src/server/auth/config.ts`
now forces it; the caller gets a fresh session (not 2FA-verified, so staff sign in again for
`/admin`). The same integration test file now also proves session-token rotation on sign-in
(no fixation) and server-side deletion on sign-out.

### F-07 — Tokens in page URLs and analytics

Signed links carry secrets in the URL: order access `?t=` (result and lookup pages, also the
gateway return URL), newsletter `?s=&t=`, password reset `?token=`, review invitations
`/danh-gia/<token>`. GA4 and the Meta Pixel record `page_location`; with consent given, the
token would reach Google/Meta. `TagManager` no longer starts on a page whose URL carries one
of these (`urlCarriesSecret` in `src/lib/privacy/cookie-consent.ts`); it starts on the next
clean page (in-app navigations never carry tokens; signed links are full page loads).
**Open (configuration):** a later full page load still reports the token page as
`page_referrer`. The GTM container must redact query strings (`t`, `token`, `s`, `e`) from
`page_location` / `page_referrer` and exclude `/danh-gia/*`, `/en/review/*` — added to
docs/ops/production-checklist.md.

### F-08 — Upload route read the body before authorising

`/api/admin/media` called `request.formData()` before `requirePermission`, and compared
`Content-Length` only when present: an anonymous chunked request with a valid-looking Origin
(trivial outside a browser) was buffered whole. It now requires a declared length ≤ 10 MB
(411/413 otherwise) and a 2FA-verified staff session before the body is read.

### F-09 — Unbounded body reads before signature checks

`/api/internal/revalidate` and `/api/webhooks/payos` read `request.text()` and only then
compared the length, so the limit did not bound memory. `readTextWithLimit`
(`src/server/lib/read-body.ts`) refuses a declared length above the limit and stops reading
a stream as soon as it is passed (tests stream 1 MB and assert reading stopped early).

### F-10 — Cookie flags

Session, cart and order-access cookies were already `HttpOnly; SameSite=Lax; Secure` in
production; `cookie_consent` is Secure on https. `NEXT_LOCALE` (next-intl) and
`announcement_dismissed` (written by the browser) had no `Secure`, which ZAP rule 10011
(FAIL) reports on the staging (https) scan. `NEXT_LOCALE` is now Secure in production builds
(browsers accept Secure cookies from `http://localhost`, so E2E and the CI scan still work);
the announcement cookie whenever the page is served over https.

### F-11 — Dotted paths reached pages with an invalid locale

Found in the server log of the production-build E2E run. The proxy skips paths with a dot,
so `/wp-login.php` matched `/[locale]` with `locale = "wp-login.php"` (and `/x.y/perfumes`
the listing). The layout answered 404, but the home page and five other pages cast
`params.locale` and still ran their streamed sections, which failed on the `locale` enum
(`22P02`) and logged a stack per probe — noise for every bot and a needless DB round-trip.
They now use `resolveLocale` (404 on an unknown locale); the E2E 404 check for
`/wp-login.php` and `/en/missing.html` now leaves the server log clean.

## Production build E2E run

Full suite against the production build (`pnpm build`, standalone server, desktop + mobile +
admin): 308 passed, 6 skipped. The only server errors were F-11; the only warnings were
expected (`User not found` from wrong-password tests, `auth.email.not_configured` in the E2E
environment). A console probe of 29 key pages (vi + en, 375 and 1280 px) reported no console
errors or warnings apart from the expected 404 status of the not-found pages.

## Residual risks and notes

- **R-01 Anonymous carts.** Cart mutations have no per-IP limit and no prune job: a bot can
  create many guest carts. Impact is table growth only (no PII, no money). Mitigated by the
  Cloudflare WAF / bot fight mode; a `carts` prune job for expired guest carts is
  recommended after go-live.
- **R-02 Order-access tokens** are a non-expiring HMAC of the order code (M2 design): anyone
  with an e-mailed link can view that order. Rotating `BETTER_AUTH_SECRET` revokes all links.
- **R-03 TOTP enrolment** happens after a password-only sign-in (invitation or an owner's
  2FA reset). Whoever knows the password at that moment can enrol; mitigated by single-use
  invitations, owner-only resets that revoke sessions, and the audit log.
- **R-04 `'unsafe-inline'` scripts** are accepted in ADR-0024 (no nonces with Cache
  Components); XSS defence rests on React escaping and the rich-text allowlist.
- **R-05 Admin session lifetime** is enforced as 8 h after sign-in (absolute), stricter than
  the "8 h idle" wording of §12, which now says so.
- **R-06** Gateway source IPs are logged on rejected webhooks (gateway servers, not
  customers).
